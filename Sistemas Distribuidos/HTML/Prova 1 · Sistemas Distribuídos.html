Introdução (aula 02)

Definição

Coleção de elementos de computação autônomos (nós) que os usuários veem como um sistema único e coerente. Consequência direta da autonomia: não há relógio global, o que causa os problemas de sincronização e coordenação.

Overlay e middleware

  • Rede overlay: cada nó conversa só com seus vizinhos lógicos, independente da rede física. Estruturada: vizinhos bem definidos (anel, árvore). Não estruturada: vizinhos aleatórios.
  • Middleware: o “SO do sistema distribuído”, camada entre aplicações e SOs locais com funções que nenhuma aplicação precisa reimplementar (replicação, segurança, comunicação, broadcast).

Quatro objetivos

1. Compartilhar recursos · 2. Transparência de distribuição · 3. Abertura · 4. Escalabilidade.

TransparênciaEsconde…
Acessodiferenças de representação de dados e de forma de invocação
Localizaçãoonde o objeto está
Relocalizaçãoque o objeto pode ser movido enquanto está em uso
Migraçãoque o objeto pode ser movido para outro lugar
Replicaçãoque o objeto é replicado
Concorrênciaque o objeto é compartilhado por usuários independentes
Falhasa falha e a recuperação de um objeto

Transparência total nem sempre é desejável: serviços baseados em localização, fusos horários diferentes, ou mostrar ao usuário que o servidor caiu.

Abertura: interfaces bem definidas, portabilidade, fácil de estender, interoperável.

Escalabilidade

  • Três dimensões (Neuman 1994): tamanho (nº de usuários/processos), geográfica (distância: latência, WAN pouco confiável, sem broadcast), administrativa (domínios com políticas conflitantes, ex. LGPD).
  • A maioria escala só em tamanho, com máquinas mais potentes (scale-up/“scale-in”). Scale-out = adicionar máquinas.
  • Técnicas: (1) esconder latência com comunicação assíncrona e handlers multithread; (2) particionar dados e computação (DNS, WWW, sharding, microsserviços, mover código ao cliente); (3) replicar/cachear.
  • O problema: réplicas geram inconsistência; manter consistência exige sincronização global, que não escala. Tolerar inconsistência depende da aplicação.
  • Sistema descentralizado: ninguém tem o estado completo, decisões só com informação local, falha de uma máquina não derruba o algoritmo, sem relógio global.

Modelos de sistema (não confundir com comunicação síncrona/assíncrona)

  • Síncrono: limites de tempo de transmissão e processamento conhecidos (LAN, datacenter).
  • Assíncrono: sem limites (Internet).
  • Parcialmente síncrono: começa assíncrono, eventualmente se comporta como síncrono.

As 8 falácias

Rede confiável · segura · homogênea · topologia não muda · latência zero · banda infinita · custo de transporte zero · existe um administrador.

Sistemas de informação

  • Palavras-chave: transação e integração.
  • ACID: Atomicidade (tudo ou nada), Consistência (transição válida; estados intermediários inválidos são permitidos), Isolamento (como se fossem em série), Durabilidade (sobrevive a falhas).
  • Transações aninhadas: subtransações em bancos independentes (companhia aérea + hotel). TP Monitor coordena a transação distribuída.
  • EAI: integração direta entre aplicações via RPC (Java RMI, gRPC) ou MOM. Proxy: componente que encaminha requisições ao servidor responsável.

Pervasivos (IoT)

  • Ubíquo: sempre presente; mudança de contexto, autonomia, inteligência emergente (flocking).
  • Móvel: sem fio, localização muda (descoberta), redes tolerantes a disrupção. Pessoas voltam ao mesmo lugar em 24/48/72 h.
  • Sensores: muitos, simples, com bateria. Dados ao operador (a) ou processamento nos sensores, que respondem só à consulta (b).
Arquiteturas (aula 04)

Estilos arquiteturais

  1. Camadas: requisição desce, resposta sobe. Usado em cliente-servidor.
  2. Objetos: objetos chamam métodos uns dos outros (RMI, microsserviços). Encapsulamento.
  3. Eventos e dados: publish/subscribe desacopla na referência (processos anônimos); espaço de dados compartilhado (Linda) desacopla na referência e no tempo (não precisam estar ativos juntos).
  4. Recursos (REST): nomeação única (URI), mesma interface para todos, servidor esquece quem chamou (stateless). Nos slides: PUT cria, GET lê, DELETE apaga, POST modifica. Exemplo: S3 (http://Bucket.s3.amazonaws.com/Objeto).

Centralizadas

Cliente-servidor: requisição/resposta, cliente espera. Um processo pode ser cliente e servidor ao mesmo tempo. 3 camadas lógicas: apresentação, negócio, dados. Camadas físicas: 1 (mainframe/terminal burro), 2 (cliente + servidor, configurações a–e conforme quanto fica no cliente), 3 (cada camada numa máquina).

Descentralizadas (P2P)

  • Peer é cliente e servidor ao mesmo tempo. Quase sempre é uma overlay.
  • Estruturado: nós seguem uma estrutura de dados distribuída (anel, árvore, DHT). Operação LOOKUP(key). Ex.: Chord, Dynamo.
  • Não estruturado: grafo aleatório; cada nó tem visão parcial de c vizinhos e troca vizinhos via gossip. Busca por flooding ou random walk. Ex.: Gnutella.
  • Superpeers: alguns nós com papel especial (índice, monitoramento, conexões). Ex.: Skype antigo.

Híbridas

  • Edge servers / CDN: cliente-servidor com servidores de borda perto do usuário.
  • BitTorrent (C-S + P2P): página Web → arquivo .torrent → tracker devolve lista de nós com o arquivo → o nó entra no swarm e troca pedaços em paralelo.

Arquitetura × middleware

  • Interceptor: intercepta o fluxo normal ao invocar objeto remoto (nível de requisição ou de mensagem) para adaptar o comportamento, ex. replicar a chamada.
  • Wrapper (adaptador): interface que torna o componente acessível às outras aplicações; ligar N aplicações par a par precisa de até N(N−1) wrappers. Broker: componente central que faz as conversões; cada aplicação precisa de um só adaptador (2N no total).
Processos e threads (aula 05)
  • Processo: memória isolada (segurança). Thread: várias linhas de execução no mesmo processo, compartilhando memória.
  • Troca de contexto entre threads é barata (IP + registradores); entre processos é cara (tabela de páginas, etc.). Processos ainda podem ser preferíveis para isolamento (Chrome).
  • Memória compartilhada → condição de corrida (id++ não é atômico). Solução: lock, semáforo, monitor, evitando deadlock.
  • Por que threads em SD: evitar bloqueio em E/S, explorar paralelismo, evitar troca de contexto entre processos.
  • Cliente multithread: navegador baixa cada recurso numa thread; várias RPCs simultâneas a servidores diferentes dão speed-up quase linear.
  • Servidor dispatcher/worker: um despachante recebe e entrega a uma thread operária. A estrutura compartilhada entre workers tem condição de corrida.
  • Servidor iterativo (uma requisição por vez) × concorrente (dispatcher). Concorrente é o mais comum.

Stateless × stateful

Stateless
Não guarda estado do cliente: não lembra arquivo aberto, não promete invalidar cache, não rastreia clientes. Cliente e servidor independentes, menos inconsistência após falhas. Perde desempenho (sem prefetching).
Stateful
Guarda estado: arquivos abertos (prefetching), sabe quem tem cache e permite cópias locais. Desempenho muito alto; o problema passa a ser inconsistência e recuperação após falha.

Clusters de servidores

3 camadas: switch lógico/load balancer (round-robin, ociosidade, sessão) → servidores de aplicação → arquivos/BD distribuídos. Frontend sobrecarrega: switch de transporte só redireciona; distribuição por conteúdo escolhe o backend pelo conteúdo e faz TCP handoff.

Comunicação (aula 06)

Tipos

  • TCP: orientado a conexão, confiável, fluxo. UDP: datagrama, best-effort.
  • Transiente: descarta se não entregar. Persistente: armazena até entregar.
  • Síncrona: três pontos onde o cliente pode bloquear: no envio, na entrega ao servidor, ou após o processamento.

RPC: os 10 passos

1 cliente chama o stub          6 servidor executa e devolve ao stub
2 stub empacota (marshaling)    7 stub empacota o resultado
3 SO envia ao SO remoto         8 SO envia ao SO do cliente
4 SO remoto entrega ao stub     9 SO do cliente entrega ao stub
5 stub desempacota e chama      10 stub desempacota e retorna
  • Concorrência: em geral (Java RMI) dispatcher/worker, uma thread por requisição → proteger variáveis compartilhadas.
  • RPC assíncrono: servidor só confirma o recebimento; cliente segue. Síncrono diferido: cliente segue e o servidor chama o cliente de volta com outra RPC de mão única (ou o cliente faz poll). Multicast RPC: mesma chamada a vários servidores.
  • Java RMI: interface extends Remote (métodos lançam RemoteException); implementação extends UnicastRemoteObject; servidor faz createRegistry + bind; cliente faz getRegistry + lookup.
  • gRPC (Google, 2015): IDL com Protocol Buffers, mensagens bem menores e mais rápidas que REST/JSON.

MOM (filas)

Comunicação assíncrona e persistente. Primitivas: PUT (adiciona), GET (bloqueia até ter mensagem e remove), POLL (verifica, nunca bloqueia), NOTIFY (instala tratador). Message broker converte formatos e gerencia filas.

Kafka: tópico = log append-only; consumidor lê pelo offset; broker é stateless; partições (sharding) escolhidas pelo produtor via hash da chave; replicação com um líder (lê/escreve) e N seguidores (só para falhas). ActiveMQ: queue (ponto a ponto, um consumidor recebe) × topic (todos os assinantes recebem).

Multicast: ordens de entrega

  • FIFO: se o mesmo processo envia m1 e depois m2, todos entregam m1 antes de m2. Mensagens de remetentes diferentes podem chegar em qualquer ordem.
  • Causal: se m1 precede causalmente m2 (ex.: P2 recebeu m1 e então enviou m2), todos entregam m1 antes. Não depende do remetente.
  • Total: todos entregam todas as mensagens na mesma ordem, qualquer que seja.
  • Receber ≠ entregar: receber vem da rede; entregar é a decisão do middleware de repassar à aplicação.

Gossip / protocolos epidêmicos

  • Anti-entropy: cada nó escolhe periodicamente outro aleatório e troca estado. Pull (só pede), push (só envia), push-pull (ambos): O(log N) rodadas.
  • Rumor: nó atualizado espalha; se o contatado já sabia, para com probabilidade pstop. Fração que nunca recebe: s = e^{−(1/pstop+1)(1−s)}. Com 1/pstop=1, ≈20% (2032 de 10.000) ficam sem a atualização: rumor sozinho não garante todos.
  • Remover dados em gossip é difícil: a remoção apaga a informação e uma réplica antiga “ressuscita” o dado. Solução: certificados de óbito (registro da remoção).
Nomeação (aula 09)
  • Nome denota entidade; ponto de acesso é identificado por um endereço.
  • Identificador: (1) refere-se a no máximo uma entidade; (2) cada entidade tem no máximo um identificador; (3) sempre a mesma entidade, sem reutilização. Telefone celular não é bom identificador: números são reaproveitados e uma pessoa pode ter vários.

Localizar nomes planos

  1. Broadcast (ARP): todos escutam; não escala além da LAN.
  2. Flooding com TTL: envia aos vizinhos, ignora repetidas, decrementa TTL. Gnutella: 7 vizinhos, TTL=10, resposta volta pelo caminho inverso, download direto via HTTP. Problema de escalabilidade de tamanho e geográfica.
  3. DHT (Chord): O(log N).
  4. HLS: árvore de domínios; a raiz conhece todas as entidades. Consulta: começa na folha local, sobe até achar registro e desce pelos ponteiros. Inserção: sobe até o primeiro nó que conhece E e cria cadeia de ponteiros até a folha.

Iterativa
Cliente pergunta à raiz, recebe o endereço do próximo servidor e pergunta a ele, e assim por diante. Cliente faz todo o trabalho; muitas mensagens de longa distância partindo do cliente.
Recursiva
Cada servidor repassa ao próximo e devolve o resultado. Mais carga nos servidores, mas cache muito eficaz (cada servidor guarda resultados intermediários) e menos comunicação de longa distância do cliente.

Registros: SOA, A, MX, SRV, NS, CNAME, PTR, HINFO, TXT. Escalabilidade de tamanho: replicar os níveis altos (mudam pouco).

DHT Chord (aula 09)
  • Espaço de identificadores {0 … 2m−1} em anel módulo 2m. Nós e chaves recebem id pela mesma hash H.
  • succ(k) = primeiro nó com id ≥ k no sentido horário. A chave k fica no nó succ(k); cada nó n é responsável por (pred, n].
  • Invariante: todo nó conhece seu sucessor. Só com sucessor, a busca é O(N).
  • Fingertable: FTp[i] = succ(p + 2i−1), i = 1..m (distâncias 1, 2, 4, 8…). Busca em O(log N) saltos (log₂ 10⁶ ≈ 20).
  • Roteamento: encaminhar ao maior finger que fica em (n, k) (closestPrecedingNode). Se k ∈ (n, sucessor], o sucessor é o responsável.
  • Consistent hashing: entrar ou sair um nó move só O(K/N) chaves. Com H(key) % N, mudar N remapeia quase todas as chaves.
  • Elimina o SPOF de uma tabela hash num servidor só e dá particionamento (sharding).

Lista 2 · Q5C · Algoritmo assíncrono da busca no Chord P1
// Estrutura do nó (atributos)
No {
  int meuId; No predecessor; No sucessor
  No[] FT            // FT[i] = succ(meuId + 2^(i-1)), i = 1..M
  KV  tabela         // pares chave-valor que este nó guarda
}

// RPC assíncrona: alguém pergunta quem é o responsável por id
procedure n.findSuccessor(id, No ini)
  if id ∈ (n, sucessor] then
     ini.response(id, sucessor)           // RPC ao iniciador
  else
     m = closestPrecedingNode(id)         // método LOCAL
     m.findSuccessor(id, ini)             // RPC assíncrona, não espera

// método local
procedure n.closestPrecedingNode(id)
  for i = M downto 1
     if FT[i] ∈ (n, id) then return FT[i]
  return sucessor

// evento: chega a resposta no iniciador
procedure n.response(id, No resp)
  if op == put then resp.store(id, valor)    // RPC
  else if op == get then resp.retrieve(id, n) // RPC; valor chega em outro evento

procedure n.get(chave)
  op = get; id = H(chave)
  findSuccessor(id, n)

Nos slides o closestPrecedingNode retorna n se nenhum finger servir; retornar o sucessor evita mandar a mensagem para si mesmo. Qualquer um dos dois é aceitável se você explicar.

Lista 2 · Q6 · Módulo, SHA1, MD5 como mapeamento chave-valor P1

Módulo: nó = H(chave) % N. Simples e distribui bem, mas quando N muda (nó entra ou sai) quase todas as chaves mudam de nó e precisam ser transferidas. Útil com conjunto fixo de servidores ou partições fixas (ex. partições de tópico no Kafka).

SHA-1: hash criptográfica de 160 bits. Usada no Chord para gerar ids de nós (ex. hash do IP:porta) e de chaves no mesmo espaço; a saída uniforme espalha bem as chaves pelo anel e, com consistent hashing, só O(K/N) chaves migram.

MD5: hash de 128 bits, mesma ideia (espaço de ids de 128 bits, por isso “normalmente M = 128”). Mais rápida, mas quebrada para segurança; serve para distribuição de chaves, não para integridade contra ataque.

Lista 2 · Q8 · Interoperável, portável, robusta, escalável P1

Interoperável: componentes de fabricantes ou implementações diferentes trabalham juntos seguindo apenas um padrão/interface comum.

Portável: uma aplicação feita para um sistema roda, sem mudanças, em outro sistema que implementa as mesmas interfaces.

Robusta: continua funcionando corretamente diante de falhas e entradas inesperadas (transparência de falhas, tolerância a falhas).

Escalável: mantém desempenho aceitável ao crescer em tamanho, distância geográfica ou domínios administrativos. Diga sempre em qual das três dimensões.

Lista 2 · Q9 · Stateless × stateful P1

O servidor stateless trata cada requisição de forma independente e não guarda nada do cliente: não registra arquivos abertos, não promete invalidar cache do cliente, não rastreia clientes. Responsabilidade do cliente enviar todo o contexto em cada requisição. Falhas afetam menos e qualquer réplica atende (fácil de balancear).

O stateful guarda estado (sessão, arquivos abertos, quem tem cache). Responsável por manter e recuperar esse estado. Ganha desempenho (prefetching, cache no cliente); se cair, o estado se perde e precisa ser recuperado, e o balanceador precisa mandar o cliente ao mesmo servidor (sessão).

Lista 2 · Q10 · BitTorrent P1

Seeder × leecher: seeder tem o arquivo completo e só envia; leecher ainda está baixando e envia os pedaços que já tem.

Tracker: servidor que mantém a lista de peers do swarm de um arquivo; não guarda o arquivo.

Servidor Web: hospeda o arquivo .torrent (metadados: pedaços, hashes, endereço do tracker), ponto de entrada da busca.

Tit-for-tat: o peer envia preferencialmente a quem mais lhe envia (unchoke dos melhores), com um unchoke otimista aleatório para descobrir novos parceiros. Combate free-riders.

Rarest-first: baixar primeiro o pedaço mais raro entre os vizinhos, para que ele não suma se o único dono sair e para equilibrar a disponibilidade.

BitTorrent tem aula própria no plano, depois de Chord. Se ainda não foi dada, pode ficar para a P2.

Extra · Ordens de multicast P1

P1 envia m1 e depois m2. P4 envia m3 e depois m4. Entregas: P2 = m1, m3, m2, m4; P3 = m3, m1, m2, m4. É FIFO? É total?

FIFO sim: em ambos m1 vem antes de m2 e m3 antes de m4. Total não: P2 entrega m1 antes de m3 e P3 entrega m3 antes de m1.

Causal: se P2 recebe m1 e só então envia m2, todo processo precisa entregar m1 antes de m2, mesmo m1 e m2 vindo de remetentes diferentes. Se P3 entregar m2 antes de m1, viola a ordem causal.

Extra · Pseudocódigo de gossip (push-pull) P1
procedure n.run()                  // main do nó
  while true
     sleepMs(x)
     executeGossip()

procedure n.executeGossip()        // local
  p = selectNode()                  // aleatório da visão parcial
  p.shareInfo(getLocalInfo(), n)    // RPC assíncrona (push)

procedure n.shareInfo(info, q)     // evento: vários podem chamar ao mesmo tempo
  addInfo(info)                     // proteger com lock
  q.updateInfo(getLocalInfo())      // RPC de volta (pull)

procedure n.updateInfo(info)        // evento
  addInfo(info)
